Security report triage for maintainers

Run the report before you read it.

reprobot builds the exact commit with sanitizers and runs the proof of concept in a sandbox with no network. A report that crashes as claimed gets read first. A report that does not crash, does not. No model decides anything: it either crashes or it does not.

Source on GitHub Read the design

A report that reads well and a real bug look the same on paper.

Open source projects now get more security reports than they can read, and many are automated reports about bugs that do not exist. Checking each one by hand is the work that is burning maintainers out.

The fix

Ask for a reproducer and run it. A made-up bug cannot produce a crash. reprobot makes that rule cheap to enforce.

How it works

Same reproducer, two commits.

The test fixture is a small C parser that copies up to 255 bytes into a 16 byte heap buffer. Real output from reprobot run on the vulnerable commit and on the commit that adds the length check.

From a repro.yaml to a verdict.

The reporter picks a commit, a build profile by name, a command and the input files. The maintainers own the build profiles, so a reporter cannot change build flags or patch the source.

Validate

Strict schema, safe paths, size limits. The command must be a program the project builds.

Claim check

Do the functions, files and line numbers the report cites exist at that commit? Checked with git, no build needed.

Build

The exact commit with ASan or UBSan, no network, cached by commit, profile and image digest.

Run

Several times, each in a fresh container: no network, read-only root, no capabilities, unprivileged user, time and memory limits.

Verdict

The crash kind and stack are compared with the claim. Same stack, same signature, so duplicates group together.

A pasted report cannot fake a crash.

The reporter controls the input, and many programs print bad input in their error messages. So reprobot never reads crashes from stdout or stderr.

Only built programs run

A shell, or any other program from the image, is rejected before anything runs.

A secret log directory

The sanitizer writes its report into a directory with a random 128-bit name that the program cannot list.

A secret exit code

Each run gets a random sanitizer exit code. A report only counts when the program exits with it.

Tested on real builds: a program that echoes a real captured ASan report on the fixed commit gives NOT_REPRODUCED, and a reporter's sh -c command gives INVALID_INPUT. Before this defence, both came back as reproduced.

Verdicts.

reprobot only judges claims it can test. A real logic bug is never labelled fake.

REPRODUCED_AS_CLAIMEDCrashed with the claimed kind and frame.
REPRODUCED_DIFFERENTCrashed, but not as the report says.
NOT_REPRODUCEDNo run crashed.
FLAKYSome runs crashed, some did not.
TIMEOUT / OOMHit a limit. May be a real hang, so it is never called fake.
BUILD_FAILEDThe profile did not build at that commit.
INVALID_INPUTBad file, unknown commit, or a command the project does not build.
OUT_OF_SCOPEThe claim is not a crash, so running it cannot test it.

Try it.

Needs Go 1.26, git and Docker. The repo has a complete example project with a planted bug.

install and run
go install github.com/DCchoudhury15/reprobot/cmd/reprobot@latest

reprobot run --project project.yaml repro.yaml
reprobot run --json --project project.yaml repro.yaml

# the service: intake API, Postgres job queue, workers
reprobot serve  --db $DATABASE_URL --data ./data --projects ./projects
reprobot worker --db $DATABASE_URL --data ./data --projects ./projects
repro.yaml
version: 1
project: tinyparse
commit: d2ea08b
profile: asan
run:
  cmd: ["bin/tinyparse", "poc/input.bin"]
  timeout_seconds: 20
  repeat: 3
files:
  - input.bin
claim:
  sanitizer: address
  kind: heap-buffer-overflow
  frame: parse_header
